# Reparación del JAR autónomo (2026-10-23)

## Diagnóstico confirmado

- `2910d9c2888778cb28fa7aade333ff3693036dcd9ad910f1ca33c0e783286260` era el SHA-256 de una biblioteca anterior. Sigue en `fabric/run/config/fsr4linux-runtime/lib/libfsr4linux.so` y estaba escrito en `FsrBootstrap.java`.
- `31789e236be1c08d696b218bc10de007683c99915e59a9267e07796f7f6a4e52` era el SHA-256 del recurso `libfsr4linux.so` tanto en el JAR anterior como en `fabric/src/main/resources` y `build/lib` antes de esta reparación. Este binario exportaba `fsr4_disable_shared_fence`.
- Prism, instancia `6767`, registró el fallo de bootstrap a las 16:14:41. Al detectar el hash incorrecto, el bootstrap eliminaba el destino y no arrancaba el bridge.
- No había una fuente de verdad generada para los hashes. El código Java y los recursos podían divergir.

## Correcciones

- `fabric/build.gradle` invoca el build nativo, sincroniza sus bibliotecas con los recursos, crea `SHA256SUMS` durante `processResources` y verifica todos los recursos dentro del JAR; `check` y `remapJar` dependen de esa verificación.
- La caché de configuración de Gradle se desactivó para que la generación de recursos y hashes se ejecute de forma predecible; el script nativo copia las DLL precompiladas actuales en cada build.
- `FsrBootstrap` exige el manifiesto completo y verifica los siete recursos. Instala desde un archivo temporal del mismo directorio; si el destino ya existe, guarda una copia `.bak` mediante movimiento atómico y reemplaza el destino mediante otro movimiento atómico. Un segundo arranque conserva la biblioteca correcta y el respaldo.
- `fsr4_abi_info` permite a Java validar versión de ABI C, versión IPC y tamaños/alineaciones antes de crear el helper. Hay aserciones de compilación para Linux y MinGW.
- Flatpak ya no desactiva automáticamente el shared fence. Se comprueban las capacidades Vulkan y el self test; la ruta CPU sigue disponible si fallan. Los errores `pidfd_open`/`pidfd_getfd` se registran una vez.
- Los timeouts IPC de asignación y self test se redujeron de 30/10 s a 4/3 s. Una respuesta corrupta o tardía invalida el helper. La interfaz muestra `ACTIVANDO` hasta que el proveedor informa el primer cuadro procesado.

## Comprobaciones realizadas

## Límites y trabajo pendiente

- Gradle no pudo iniciar en el sandbox: no hay interfaz de red utilizable para `FileLockContentionHandler`. El script se analizó con Groovy, Java se compiló con `javac` y el JAR candidato se reconstruyó sobre el JAR anterior. La tarea Gradle nueva todavía debe ejecutarse en un entorno con red local disponible.
- El sandbox de esta sesión no expone `/dev/dri`, aunque la sesión del usuario es Wayland y la configuración de Flatpak de Prism declara `devices=all`. El intento `flatpak run` desde aquí falló con `Unable to allocate instance id`. El log real de Prism demuestra el arranque anterior del JAR y Vulkan; la nueva corrección del fence no se ha ejecutado dentro de Prism. No hay mediciones nuevas de FSR 4.1.1/3.1.5, FG ×2/×3/×4, rendimiento o estabilidad.
- El log real de Prism `6767` (16:56–16:57) confirmó bootstrap, RX 9060 XT con RADV/Vulkan y helper que ofrece 4.1.1/3.1.5. El self test del shared fence falló con contador cero y después `gpuAlloc` recibió `bridge not running`. El self test enviaba un `D3D12 queue Wait(1)` sobre un fence cuyo descriptor importado no estaba probado: esa espera impedía que avanzara incluso la señal de finalización del helper, así que el timeout IPC lo mataba. El self test ahora comprueba primero el contador sin bloquear la cola y prueba hasta ocho descriptores. Si ninguno corresponde, informa el fallo y deja al helper vivo para la ruta CPU. La razón por la que el descriptor inicial no corresponde todavía necesita una prueba real. Una segunda prueba en Prism a las 17:02–17:03 confirmó que la ruta CPU seguía con el helper vivo, pero la primera solicitud de asignación expiraba tras cuatro segundos sin respuesta. La función de asignación llamaba a esperas de cola incluso sin recursos anteriores; se eliminaron esas esperas vacías y se añadieron logs de cada etapa de creación de texturas. Los errores IPC de asignación ahora indican explícitamente `helper timeout`, `helper died` o `request rejected` en vez de dejar un mensaje vacío. Los logs del helper ahora se anexan en cada reinicio, con PID de sesión, para conservar el punto exacto del bloqueo. Un tercer log real (17:08–17:10) mostró que la asignación de las cuatro texturas sí termina, pero la solicitud de self test expiraba. El helper hacía cuatro copias/readbacks GPU con cuatro esperas y cuatro asignaciones; se agruparon en una sola asignación, un comando y una espera, conservando el CRC de cada plano. El siguiente log real (17:08–17:10) del JAR previo ya probó que las cuatro texturas se crean y que la verificación expira; los reintentos ocultaban el primer error con `helper not running`, lo cual también se corrigió. La revisión con lectura agrupada se probó en Prism a las 17:13: el helper registró `selftest begin` y `copying 17072640 bytes`, pero no `GPU copy completed`; el IPC expiró a los 4 segundos. La ruta por defecto evita ahora el sondeo especulativo del fence, que había señalado un syncobj no identificado y podría interferir con la cola. `FSR4_SYNC=gpu` mantiene la ruta GPU solo para diagnóstico explícito. La espera del self test de D3D12 está acotada a 2,5 s e informa el valor del fence y `GetDeviceRemovedReason`. Esta revisión aún no se ha probado en Prism. `helper alloc failed` y `shared texture setup failed` posteriores pueden depender de `pidfd_getfd`, DMA-BUF o Vulkan external memory.
- Persisten posibles esperas de GPU (`vkQueueWaitIdle`) fuera de los timeouts IPC. No está demostrado que todos los modos estén libres de bloqueos.
- El sandbox permite escribir solo dentro del árbol exportado. `~/Escritorio/Minecraft-FSR4-Beta.jar` no se reemplazó. `release/Minecraft-FSR4-Beta.before-repair.jar` es la copia exacta del JAR anterior.

## Entrega: helper sin ventana de consola

- Causa: `fsr4_bridge.exe` estaba enlazado como `Windows CUI` (subsistema PE 3). Wine abría una ventana de consola negra. El helper escribe su log en archivo mediante `freopen`, por lo que no necesita consola visible.
- Único cambio funcional de esta revisión: `scripts/build-native.sh` enlaza el helper con `-mwindows`. `objdump` confirma `Windows GUI` (subsistema PE 2), y `nm` confirma tanto `WinMainCRTStartup` como `main`; no se cambiaron IPC, renderizado ni proveedor AMD.
- Último registro de Prism 6767 antes de esta revisión: FSR 4.1.1 procesó un cuadro y FG propios ×3/×4 se activaron; no contiene errores del mod. El prefijo privado ya contiene `amdxcffx64.dll` de 65,657,608 bytes, obtenido por GE-Proton. Este registro no demuestra aún FG ×2 ni que la nueva compilación suprima visualmente la ventana.
